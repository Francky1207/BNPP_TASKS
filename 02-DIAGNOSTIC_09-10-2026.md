#### Dette technique
- Huit dépôts, NuGet privé pour 206 lignes de code partagé, deux versions de Shared.Domain (1.0.0 et 1.1.0) en production simultanée : complexité de microservices sans aucun de leurs bénéfices.
- `DoctoZen.MedicalRecords/` contient un niveau de dossier en double (`src/`, `tests/` vides à la racine, vraie solution dans `Doctozen.MedicalRecord/`) ; nommage incohérent (`SurgerieService`, `ISurgerieService`, `ObjetResponse`).
- Client : un composant de 3 436 lignes, environ 270 avertissements de nullabilité, `NavMenu` du template par défaut (Counter/Weather) jamais nettoyé, pages vides routées.
- Scripts obsolètes : `tools/run-all-services.ps1` pointe vers des chemins inexistants ; scripts `1-…14-*.ps1` d'organisation Git à la racine.
- Branche Auth active `feature/auth-demo-20260415` alors que le dernier travail est du 06/06 : la stratégie de branches est à clarifier. Modification non commitée : `MedicalRecords.API/appsettings.json`.
- Packages incohérents : FluentValidation 12 mélangé avec FluentValidation.AspNetCore 11, Serilog.AspNetCore 10 sur net8, EF 8.0.0 sans correctifs de sécurité (8.0.x à jour recommandée).
- Pas de CI exploitable (un workflow GitHub dans MR seulement), pas de Docker, pas de health checks.

#### Performance
- Blazor Server : un circuit SignalR par utilisateur, avec de la mémoire serveur par session ; **inadapté au 2G/3G instable et au hors ligne** (reconnexions, latence à chaque clic).
- Le front appelle deux API sur deux origines : double latence TLS, CORS ; pas de compression de réponse configurée ; pagination présente sur certaines listes seulement.
- Cache Redis implémenté côté MR (bien) mais désactivable ; aucun cache côté Auth (cache mémoire inutilisé, sauf pour la limitation de débit).
- Fichiers servis via SFTP à chaque téléchargement (connexion SSH par requête).

#### Découplage
- MR est bien découplé en interne (couches propres).
- Entre modules : aucun appel direct ; l'identité patient passe par un `PatientId` (GUID) sans contrat. La recherche de patients s'est retrouvée dans Auth faute de module « Utilisateurs » : fuite de responsabilité.
- Shared.Contracts et Shared.Infrastructure existent mais ne sont pas utilisés ; pas d'événements (le RabbitMQ prévu n'existe pas).
- Verdict : **découplage logique correct pour MR, nul ailleurs** ; la frontière physique (8 dépôts, 2 bases, 2 hôtes) coûte plus qu'elle ne protège.

## PARTIE 4 : NOVA (référence, `C:\wamp64\www\nova`)

### 4.1 Architecture
PWA mobile-first de gestion de tâches à la voix. **PHP 8.3-FPM sans framework** (`api/*.php` : un fichier par endpoint, `core/*.php` pour le métier), **MySQL 8**, **JS vanilla ES2022 sans build** (`public/app.js` + modules), service worker (`sw.js`, cache versionné `nova-v122`, IndexedDB, Background Sync, Web Push VAPID), crons Linux sous `flock` (rappels toutes les 15 min, synchronisation Google Calendar toutes les 30 min), PHPMailer, Google Calendar API. Documentation de maintenance exemplaire (`docs/01` à `15`, `CLAUDE.md`).

### 4.2 Voix et IA
- **Capture** : `MediaRecorder` (webm), appui long sur le FAB (seuil 200 ms) ou micro de l'accueil ; saisie texte équivalente.
- **Transcription** : `POST https://api.openai.com/v1/audio/transcriptions`, `whisper-1`, `language=fr`, `temperature=0`, **prompt de biais de vocabulaire**, timeout 20 s ; nettoyage (`WhisperCleaner`) et filtre d'hallucinations (« merci d'avoir regardé »…).
- **Compréhension, en cascade pour limiter coût et latence** : (1) nettoyage du préfixe « Nova » et des hésitations ; (2) **score par règles ≥ 0,7 → décision sans LLM** (gain d'environ 5 s) ; (3) correspondance directe avec une tâche existante ; (4) sinon `IntentClassifier` → **GPT-4o-mini**, `temperature 0`, `response_format=json_object`, `max_tokens` 80 à 200, avec un **prompt contextualisé** (listes `[ID] titre` des tâches, projets et membres + bloc narratif) pour obtenir un `target_id` vérifiable ; (5) garde-fous : confiance < 0,35 → hors périmètre ou création, vétos sémantiques, vérification que la cible partage un mot avec la phrase.
- **Validation par l'utilisateur** : carte « bridge » éditable (ce que Nova a compris), confirmation automatique après 4 s, suggestions contextuelles, annulation douce ; actions groupées toujours confirmées.
- **Synthèse vocale** : `speechSynthesis` du navigateur (fr-FR, gratuit), normalisation des heures et des dates, messages serveur prioritaires, briefing vocal.
- **Quotas** : `ApiQuotaGate` + `PlanManager` (1 énoncé = 1 appel ; plans FREE/SOLO/PRO/TEAM).

### 4.3 Déploiement
VPS OVH Ubuntu 22.04 (`nova.seedkaholding.com`), Nginx + PHP-FPM + MySQL, **qui héberge déjà une application .NET Core (ARSTM) + PostgreSQL**. Script PowerShell `nova_deploy.ps1` : zip de `api/ core/ cron/ public/` sans `.env` → `scp` → copie de sauvegarde `/var/www/nova_backup_<date>` → `unzip` → `composer install --no-dev` → droits → `systemctl reload php8.3-fpm`. Sauvegarde de la base par `mysqldump` + `scp` avant migration. Retour arrière par `rsync` depuis la copie de sauvegarde. Pas de CI ; validation manuelle du diff par Franck.

### 4.4 Réutilisable dans DoctoZen
| Élément NOVA | Réutilisation DoctoZen |
|---|---|
| Pipeline voix (MediaRecorder → Whisper → règles → LLM JSON → bridge de validation → TTS navigateur) | **Assistant patient** (« prends-moi un RDV avec un pédiatre demain matin », « quand est mon prochain rappel de vaccin ? ») et **dictée médecin** (notes de consultation, constantes). À porter en C# (`HttpClient`) derrière une interface `IAssistantService` |
| Cascade règles d'abord, LLM ensuite + garde-fou de confiance | Indispensable en santé : intentions fermées (rechercher, réserver, annuler, consulter le DME) traitées sans LLM ; LLM seulement pour l'extraction d'entités |
| Prompt contextualisé avec des ID vérifiables + `json_object` + `temperature 0` | Suggestions de créneaux (le LLM choisit parmi des `slot_id` réels, jamais une date inventée) |
| Bridge éditable + confirmation explicite | Obligatoire avant toute action sur des données de santé ou un paiement (désactiver la confirmation automatique de 4 s pour ces cas) |
| `ApiQuotaGate` / `PlanManager` | Quotas d'IA par plan (patient freemium, abonnement centre) |
| Service worker : network-first + IndexedDB + `handleOfflinePatch` + Background Sync, Web Push VAPID | **Socle direct du mode hors ligne et des rappels** de DoctoZen |
| Crons de rappels (et leur dette N2/N3 : rappels non annulés) | Rappels de RDV et de vaccins ; éviter d'emblée les défauts N2–N7 (statut non filtré, fuseau horaire) |
| Procédure VPS + doc `12-deploiement` + `13-regles-et-pieges` | Même VPS possible (Nginx en reverse proxy vers Kestrel, service systemd) ; reprendre le format de documentation |

Points de vigilance propres à la santé : Whisper et GPT reçoivent du texte ou de l'audio potentiellement médical. Il faut un **consentement explicite**, la minimisation (pas de nom ni d'identifiant dans le prompt), une déclaration ARTCI et l'évaluation d'un fournisseur offrant des garanties de non-rétention (ou un modèle auto-hébergé pour la transcription). Une IA de **pré-diagnostic** relève du dispositif médical (ISO 13485 / CE) : à exclure du MVP.

## PARTIE 5 : recommandation d'architecture

| Critère (1 développeur, 1 VPS) | (a) Microservices (cible actuelle des docs) | (b) Monolithe modulaire .NET 8, une UI Razor | (c) Nouveau projet repris de l'existant |
|---|---|---|---|
| Charge d'exploitation | Très élevée : N API, N bases, gateway, broker, NuGet privé, 8 dépôts | Faible : 1 processus, 1 base, 1 déploiement | Faible (si la cible est b) |
| Vitesse de livraison | Lente (contrats, versions, CORS, jetons entre services) | Rapide (refactoring global, transactions locales) | Coût de démarrage de 2 à 3 semaines, puis rapide |
| Isolation des modules | Physique | Logique : projets séparés, schémas SQL séparés, tests d'architecture | Celle de la cible choisie |
| Hors ligne / PWA | Indépendant du découpage | Indépendant | Indépendant |
| Réutilisation de l'existant | 100 % (mais on garde la dette) | ≈ 80 % du back (entités, services, migrations MR) ; front à refaire | Idem b, avec un nettoyage plus franc |
| Risque | Dispersion, jamais de MVP | Faible ; extraction d'un module en service plus tard possible | Risque d'effet « tunnel » si on réécrit trop |

**Recommandation : (b) + (c) combinés.** Un **nouveau dépôt unique** structuré en **monolithe modulaire .NET 8**, dans lequel on **reprend** (en déplaçant, sans réécrire) le domaine, les services et les migrations de MedicalRecords et d'Authentication. L'UI unique est en **Razor côté serveur (Razor Pages / MVC + rendu statique SSR), progressivement enrichie en PWA** : JS léger, HTMX ou îlots Blazor interactifs seulement là où c'est utile. Blazor Server est écarté comme socle, car il est incompatible avec le hors ligne et coûteux en 2G/3G.

### Structure cible
```
DoctoZen/                       (1 dépôt, 1 .sln)
  src/
    DoctoZen.Web/               Hôte unique : Razor Pages + API minimal /api/v1 (PWA, mobile, futur)
      Shell/ (layout, registre de menus par profil, service worker, manifeste)
    Modules/
      Identity/     (ex-Authentication)   Domain | Application | Infrastructure | Web (pages + endpoints)
      Directory/    (users, établissements, lieux, proches, validation médecin)
      MedicalRecord/(ex-MedicalRecords : on garde les couches)
      Scheduling/   (Consultations/RDV, specs UC prêtes)
      Teleconsult/  Prescriptions/  Payments/  Notifications/  Admin/
      Assistant/    (IA, plus tard ; interface + implémentation OpenAI inspirée de NOVA)
    BuildingBlocks/ (Result, pagination, audit, chiffrement, outbox, horloge, i18n)
  tests/ (unitaires par module + tests d'architecture NetArchTest + intégration Testcontainers SQL)
  deploy/ (docker-compose.yml, nginx.conf, doctozen.service, deploy.ps1 inspiré de NOVA)
```
Règles : un module n'accède qu'aux **contrats publics** des autres (interfaces + événements en mémoire via MediatR ou un simple bus) ; **un schéma SQL par module** (`identity.*`, `mr.*`, …) dans une seule base SQL Server ; aucune clé étrangère entre schémas ; cookie d'authentification HttpOnly pour l'UI, JWT pour `/api` (mobile futur).
